# Спекуляция: итоговое решение (v4, 26.10)

Цель: для модели из списка человек видит, какие драфтеры есть, что каждый даёт на его карте и
задаче, сколько стоит памяти; по умолчанию — лучший; всё — из наших замеров, у пользователя ничего
не меряется и не угадывается.

## Что показали замеры (25–26.10, 4 карты, 4 семейства)

| Вопрос | Ответ | Замер |

## Решение

**Реестр = замеры пар, ничего не вычисляется у пользователя.** Одна запись — вариант модели
(repo@commit) + драфтер (repo@commit[/файл] или встроенный mtp), замер на одной лабораторной карте:

```json
"unsloth/Qwen3.5-9B-MTP-GGUF@9716a636": {
  "z-lab/Qwen3.5-9B-DFlash@5fc3b3d4": {
    "quants": ["Q4_K_M", "Q8_0"],                       // каждый рекомендуемый квант — свой замер R
    "k":      [1, 2, 3, 5, 7],
    "e":      {"thinking": [...], "plain": [...]},     // токенов за раунд
    "r":      {"Q4_K_M": [...], "Q8_0": [...]},         // цена раунда в шагах, ≤8 строк
    "context": [1.0, 0.87, 0.61],                        // множитель E: <1K / 1–8K / 8–24K
    "wide":   {"ada": {...}, "blackwell": {...}}         // k≥8 и нагрузка: по поколению, 2 карты
  }
}
```

**Продукт:**
- k = argmax E/R для режима запроса и длины промпта; показывает ускорение E/R и память драфтера
  (из плана — байты его тензоров); порог сторожа = R(k).
- Квант ≥4 бит без своего замера R — ближайший замеренный (выбор k теряет ≤3,5 %); <4 бит без
  замера — без спекуляции (E там падает).
- Поколение карт без замера широкой проверки — только k≤7 и один запрос.

**Удаляется:** формула цены раунда (src/spec/load_model, 415 строк), 98 профилей по классам карт,
поиск «ближайшей модели» по геометрии/словарю, угадывание ролей по именам.

**Лаборатория (сервер реестра, DECISIONS 31):** каждый вариант списка × его драфтеры ×
рекомендуемые кванты — spec-tune на одной карте (≈3 мин на пару) + широкая проверка на двух картах
поколения; перепроверка по графику.

## v5 (27.10): решения владельца и проверка на данных

Владелец: (а) непромеренный вариант — запрос на наш сервер (LLM находит драфтер в отдельном репозитории по
странице HF, решение — по проверкам фактов: отпечаток словаря, вид драфтера, слои), запрос ставит пару в очередь
замеров лаборатории; (в) замер → полный рецепт в реестре; клиент работает и офлайн, обращение к серверу
блокируется настройкой (приватность). (б) глубина для непромеренного варианта — по данным пар той же
архитектуры и вида драфтера в нужном режиме.

Проверка (б) на наших замерах (scratchpad/spec_policy.py, «исключи одного»: глубина из остальных пар группы;
группы: Qwen3.5+MTP ×3 кванта, Qwen3.5+DFlash ×5 (3 кванта, HauhauCS, Ada), Gemma 12B+ассистент ×2 карты,
gpt-oss+DFlash ×2 карты; режимы thinking / plain):
- медиана лучших глубин: потеря против своей лучшей в среднем 2,2 %, худшая 13,8 %;
- **глубина, лучшая в среднем по паре группы (k ≤ 7), с отдельным классом < 4 бит: в среднем 1,4 %**, худшие —
  Ada DFlash thinking 13,8 % (там лучшая k = 15: широкая проверка — свойство поколения) и IQ2 MTP plain 10,7 %
  (у 2-битного кванта своя глубина мельче);
- файнтюн с приёмом как у WaveCut (2,90 токена за раунд против 4,5–4,6 у базы: 0,535 от черновиков после
  первого; первое моделирование брало 0,63 — мягче факта, исправлено): без защиты ДВА режима стали бы медленнее
  обычного декода — gpt-oss plain ×0,92 и IQ2+MTP plain ×0,99; остальные ≥ ×1,18.
Решение: глубина = лучшая в среднем по парам группы и режима, k ≤ 7 (глубже — только для поколения карт с
замером широкой проверки), класс < 4 бит отдельно; если у группы смоделированный худший выигрыш < ×1,05 —
быстрый рецепт для этого режима не включается (gpt-oss plain, IQ2+MTP plain); сторож включён; GUI — «предварительно» и
диапазон ускорения по группе. Всё считается из установленного реестра — офлайн работает; сервер нужен только
для поиска драфтера в отдельном репозитории и для очереди замеров.

## Реализация v5 (план, 27.10)

Движки и сторож читают `spec::Profile` (выбор по режимам: конфигурация, порог, глубины по нагрузке) — этот
формат остаётся. Меняется ИСТОЧНИК профиля:

- сейчас: опубликованный профиль класса карты → цепочка похожих карт → «*» → поднятые пороги (медиана реестра),
  сопоставление модели по repo / lineage / nearest (геометрия+словарь); цена раунда при C>1 — round_cost_of;
- v5: профиль СТРОИТСЯ у клиента из замеров пары (реестр v2) для этой карты (поколение), кванта и режима:
  k = argmax E/R (k ≤ 7; глубже и нагрузка — только из замера широкой проверки поколения), порог = R(k);
  непромеренная пара → профиль из данных группы (движок + вид драфтера + режим + класс бит, k ≤ 7,
  выигрыш худшего ≥ ×1,05), basis = «preliminary»; иначе — без спекуляции.

Ключ пары — содержимое весов, а не коммит: sha256 LFS-файлов из листинга хаба (GGUF-файл или набор шардов) у цели
и драфтера (artifact/source_identity уже это считает); repo@commit хранится для людей и скачивания. Правка
README (новый коммит) пару не обнуляет.

PR по порядку:
- S1 — формат реестра v2 (pairs, drafters с размером и формой) и его чтение + построение Profile из пары и из
  группы; чистые функции, юнит-тесты на наших замерах (stdata). Поведение продукта не меняется.
- S2 — разрешение: serve и план берут Profile из S1 (пара по идентичности весов → группа → ничего); удаляются
  цепочка похожих карт, nearest/lineage для профилей, foreign floors, registry median. Проверка на стендах:
  список моделей — какая спекуляция выбрана и что она даёт (замер декода).
- S3 — выбор и план: скорость спекуляции в T выбора (E/R пары), память драфтера по его форме из реестра
  (исправляет занижение DFlash на ~2 ГБ в плане без весов); GUI: драфтеры, ускорение, «предварительно».
- S4 — удаление round_cost_of / modeled_load (load_model.cpp) и 98 профилей; реестр заполнен замерами пар.
- S5 — сервер: поиск драфтера в отдельном репозитории (LLM + проверки фактов), очередь замеров; клиент —
  офлайн-работа, блокировка обращений настройкой.
Лаборатория (параллельно с S1–S3): spec-tune пар списка (вариант × драфтеры × кванты), широкая проверка на двух
картах поколения.

## S3 — драфтер как ось единого выбора (проект, 27.10; владелец одобрил по DECISIONS 42)

Решение владельца: «драфтер рекомендуем по скорости, но понимаем, сколько запросили контекста и
потоков, и показываем, что выбранное не оптимально по скорости из-за контекста; одна ось».

Как это ложится в существующий выбор (`src/product/choice`, проверено по коду):
- В режиме «Авто» контекст уже ограничение: цели 32K → 16K → 8K на поток
  (`quant_own_targets`). Кандидат годен, если держит цель, дальше побеждает наибольшая ценность
  −ln T − λ·KLD. Выбранная конфигурация запускается с наибольшим контекстом, который влезает.
- Сейчас память драфтера в выборе учтена (свой контекст считает `plan_model` со спекуляцией),
  а скорость нет (`speed_of` спекуляцию не знает). Половина сделки.

Изменения:
1. **Кандидат** получает ось `drafter`: без драфтера, а также по одному варианту на каждый вид, что
   несёт модель и запускает Engine (MTP / ассистент, DFlash, DFlash2, позже DFlash-q8). Конфигурация
   и ускорение варианта:
   - есть замер пары — лучший выбор этого вида (`select()` по замерам вида);
   - иначе выбор группы (S1) или опубликованного профиля для этого вида;
   - оба для «рассуждений» и «без рассуждений» по флагу сервера.
2. **Память** — тот же `OwnContextFn`: план с этим драфтером (его веса и KV по форме, S2).
3. **Скорость** — `speed_of` умножает декод потока на ускорение варианта при данном числе потоков
   (по таблице нагрузки: где глубина 0 — множитель 1). Префилл не меняется.
4. **Точность** — без изменений: жадный вывод драфтер не меняет.
5. **Выбор** — тот же порядок: цель контекста → годные кандидаты → наибольшая ценность. Квант против
   драфтера решает λ: при почти равной цене побеждает качество.
6. **Сервер запускает выбранный драфтер:** `plan_with_speculation` берёт драфтер выбора, а не первый
   профиль. Откаты при нехватке памяти остаются.
7. **Объяснение:** `explain` показывает соседей по оси драфтера. Если самый быстрый драфтер не держит
   запрошенный контекст или потоки, план и GUI говорят: «DFlash ×2,5 не держит 32K × 2 потока —
   выбран MTP ×1,9».

Порядок работ: после #111 (S2) — ветка S3 от него. Сначала ядро выбора (кандидаты, скорость,
юнит-тесты на синтетике), затем подключение (plan_choice, plan_speculation, сервер), затем GUI.
Проверка в продукте: 9B Q4_K_M и таблица квантов на 4070 Ti / 5070 Ti, Gemma 12B, gpt-oss.

### S3, дополнение владельца (27.10): глубина для рассуждений и без них

Владелец: «можем запускать с разной длиной драфтера для думающей и не думающей сессии, если это
имеет смысл; в GUI выбирается вариант с рассуждениями или без, и показывается дельта (отклонение);
из командной строки можно задать 5:4, но только если это можно сделать и это имеет смысл».

Что уже есть (проверено по коду):
- Профиль хранит отдельные выборы `thinking` и `non_thinking`.
- `--spec-select thinking` запускает каждый запрос на глубине для его флага рассуждений тем же
  драфтером (`SpeculationMenu::pick`, `request_speculation`). Engine захватывает обе глубины.
- По умолчанию стоит `fixed`: одна глубина на все запросы.
- Явно (`--spec mtp --draft-tokens N`) задаётся одна глубина.

Решение в S3:
1. **Выбор режима глубины — часть единого выбора, по данным.** Если у драфтера выбранного вида
   глубины для рассуждений и без них различаются, Engine запускает обе, а выигрыш над одной общей
   глубиной заметен, сервер по умолчанию запускает «по запросу». Иначе — «одна глубина» (лишние
   графы не нужны). Пример по замеру: 9B Q4 + DFlash на Ada — рассуждения dflash:15 ×3,86, без них
   dflash:7 ×2,22. На чужом поколении обе глубины ≤7 совпадают, и тогда фиксированная.
2. **GUI.** Переключатель «с рассуждениями / без» выбирает, чей вариант показывать (глубина,
   ускорение, ток/с). Рядом — дельта ко второму варианту: «без рассуждений: dflash:7, ×2,2 (−1,6)».
3. **CLI.** `--draft-tokens 5:4` (рассуждения : без) принимается только если:
   - обе глубины запускаются движком для этого драфтера (MTP Qwen ≤5, DFlash ≤ блока);
   - глубины различаются: при равных отказ «одна глубина: --draft-tokens 5».
   
   Включает выбор по запросу. Иначе понятный отказ с причиной.

> Адаптивная глубина (`mtp:K:K0`) удалена по решению владельца (DECISIONS 44): на реальном тексте
> она не работает. Здесь и дальше — только фиксированные глубины.
