# Решения по единому выбору — кратко: что решено, из чего выбирал, почему

Формат: **решение** · варианты · почему. Новые решения добавляются в конец.

1. **Строю поверх PR #60 разработчика, а не заново.**
   - Варианты: свой расчёт памяти / #60.
   - #60 считает байты функциями самого планировщика семейства; моя формула на странице лишь
     повторяла их. Повтор — второй источник правды.
   - Риск: #60 ещё не в master. Моя цепочка PR стоит поверх него, сливать её можно только после #60.

2. **Как выбирать при конфликте скорости и точности: одна формула U = −ln T − λ·KLD.**
   - Вариант «самый крупный квант, что влезает» (#60): точность всегда первая. Тогда, например,
     exact-режим выиграл бы при −73 % префилла.
   - Вариант «по порядку критериев с допуском» (сначала скорость в пределах 10 %, потом точность):
     даёт самые мелкие кванты (IQ2), а если поставить точность первой — exact.
   - Взвешенная сумма с одним параметром λ: это единственный вариант без таких провалов.
     Он прямо выражает «при почти равной стоимости — качество». λ — одна константа в одном месте,
     её можно менять.
   - T — время типового запроса (промпт P + ответ G), поэтому префилл и декод входят
     в своей реальной доле.

3. **(Заменено решением 3а.) λ по умолчанию: 0,001 KLD ≈ 5 % времени запроса (λ = 50).**
   - Проверка на замерах 9B:
     - exact против fast: время +27 %, KLD −0,0039 → fast (так и надо);
     - KV bf16 против int8: на 4070 Ti время +6 % → int8; на 5070 Ti +2 % → bf16 (там почти бесплатно);
     - int8 против fp8 (память и скорость равны) → int8, он точнее.
   - Это и есть «при почти равных — качество».

3а. **Исправлено: λ = 25, а не 50 (0,001 KLD ≈ 2,5 % времени).**
   - При λ = 50 на 4070 Ti exact против fast выходила почти ничья: +26 % времени против −0,0044 KLD,
     разница в оценке 0,009. «Почти равной ценой» +26 % не назовёшь.
   - При λ = 25 точность побеждает, только если стоит меньше ~11 % времени.
   - Exact стоит +26 % на 4070 Ti и +38 % на 5070 Ti при запросе 2048 + 512 токенов, поэтому
     по умолчанию остаётся fast.

3б. **KV int8 на фоне fast почти ничего не стоит по точности, и модель это видит.**
   - Замер: fast с KV bf16 и состоянием f32 даёт KLD 0,00388; fast с KV int8 и f16 — 0,00403.
   - Корень из суммы квадратов даёт тот же порядок. Поэтому KV int8 выбирается, когда он хоть
     немного быстрее; KV bf16 — когда скорость одинаковая и памяти хватает.

4. **Форма запроса по умолчанию: P = 2048 токенов промпта, G = 512 ответа (чат).**
   - Варианты: только декод / только префилл / смесь.
   - Только декод не видит цену exact и чанка. Пользователь и GUI задают P и G сами
     (RAG — длинный P, генерация — длинный G).

5. **Квант с неизмеренной точностью.**
   - Пока нет кривой KLD по квантам, точность кванта оценивается по bpw: формула KLD(bpw),
     подогнанная по кривой 9B, как только та досчитается.
   - До этого выбор кванта откатывается к правилу #60 (самый крупный, что влезает, не ниже 3,5 bpw).
     Так поведение не меняется, пока нет данных.

6. **Кольцо и состояние не перебираются отдельно, а следуют за KV (правила владельца).**
   - Кольцо = тип KV; состояние на ступень точнее KV (bf16 → f32, иначе f16; exact → f32).
   - Флаги `--sliding-kv-dtype` и `--state-dtype` закрепляют их.
   - Причина: для fp8-кольца и для f32 против f16 при каждом KV нет замеров точности. Перебор без
     данных выдал бы случайный ответ.

7. **Без замера слагаемого точности кандидат не считается точнее.**
   - Неизвестное слагаемое берётся равным худшему известному для этой оси, а не нулю.
   - Иначе непроверенное значение выигрывало бы просто из-за отсутствия данных.

8. **Точность для семейств без замеров (Gemma, dense, Nemotron) — перенос с Qwen 9B, с пометкой.**
   - Вариант «не выбирать вовсе» оставил бы эти семейства без автоматики. Перенос честно помечен
     в объяснении. Задача на перплексию для этих семейств остаётся.

9. **Проверка — на смеси реальных задач, а не на одном бенчмарке.**
   - 8 случайных задач из examples/cli/messages: код, рассказ, перевод, CSV/SQL, чат, рассуждение,
     поиск иголки в 8K и 22K, ответы 96–512 токенов, greedy.
   - Сравнивается суммарное время всех задач (средневзвешенно) с предсказанием P/префилл + G/декод.
   - Константы на этих прогонах НЕ подгонялись. Следующая подгонка их возьмёт, а проверяться будет
     на других картах.

10. **GUI больше не считает скорость сам.**
    - Своя JS-модель полосы с подгоночными таблицами по типам моделей и калибровкой по каталогу
      удалена: её нельзя было объяснить и она расходилась с движком.
    - Скорость в таблице квантов и в выборе берётся из ядра через /api/plan. Спекуляция умножается
      на ускорение профиля реестра только для одного потока: для нескольких профиль не мерили.
    - Замеры (сравнение с llama.cpp на этой карте) остались: это данные, не модель.

11. **По правилу проекта (B1) тип KV и активации решаются по поколению карты, а не по конкретной плате.**
    - Codex указал на deterministic-decisions.md: решения, меняющие байты ответа, не читают частоту
      и полосу платы.
    - Выбор считается на «эталонной карте поколения» (среднее лабораторных карт). Все платы одного
      поколения выбирают одинаково; частота и полоса платы идут только в показываемые оценки.
    - Решает только поколение, где поправки на тип KV и exact сняты на двух картах.
      Сейчас это Ada (4070 Ti + 4090: KV совпадают в пределах 6 %, exact — в пределах 20 %).
      На Blackwell и Turing по одной карте, там остаются умолчания семейства, а GUI пишет почему.

12. **Тип KV — рычаг памяти, а не только точности.**
    - Если на первой ступени Auto (32K) крупный квант влезает только с более узким KV
      (например, nvfp4), правило берёт эту пару, а не спускается на 16K.
    - Так сохраняется порядок #60 «сначала полный контекст».
    - Цена в точности видна в панели «что изменится».

13. **В таблице квантов скорость оценивается на одной глубине для всех строк**
    (четверть запрошенного контекста, в Auto — от min(родной, 32K)).
    - Иначе строка с большим собственным контекстом выглядела медленнее только из-за этого.

14. **(Отменено, см. 14а.) Постоянная на запрос r0 = 0,135 с — только в показываемых оценках.**
    - Подогнана по смеси задач на 4090: rms 9,4 % → 3,6 % для одного потока.
    - Это константа одной карты, поэтому решения считаются без неё (принцип 4).
    - Проверка — на смесях на 2080 Ti, 4070 Ti и 5070 Ti (уже стоят в очереди).

15. **Правило владельца для связанных хранилищ — в одной функции (`coupled_storages`).**
    - Кольцо окна = тип KV: fp8 при любом KV, кроме bf16, но только у семейств, чьи кольца
      принимают fp8 (Gemma 4, плотные декодеры); у остальных bf16.
    - Состояние на ступень точнее KV: KV bf16 → f32, иначе f16; при exact — f32.
    - Флаги `--sliding-kv-dtype` и `--state-dtype` закрепляют своё значение.
    - Сервер и CLI применяют одно и то же через общие `start_axes` и `apply_start_axes`.

16. **CLI `ninferno` тоже берёт выбор.**
    - Владелец просил один код во всех местах, где нужен такой выбор.
    - CLI пишет строку «choice |», а в `--plan` выводит раздел выбора.

17. **Квант по полезности — только когда есть измеренная кривая KLD по квантам и поколение имеет
    право решать.**
    - Тогда кванты сравниваются по той же формуле, что KV и активации, а не правилом «самый
      крупный, что влезает».
    - Порог 3,5 бита и порядок ступеней контекста Auto остаются защитой качества.
    - Пока кривой нет, работает правило #60. Кривая для 9B досчитывается на 5070 Ti.

14а. **r0 убран: это расход хоста, а не карты.**
    - Проверка на 4070 Ti, где r0 не подгонялся: с r0 оценки стали хуже (+3 % → +8 %).
    - Без r0 один поток на 4070 Ti укладывается в ±5 %, включая Gemma 12B — семейство, которого
      в подгонке нет.
    - На 4090 быстрые маленькие модели (4B, 35B-A3B, 240–250 ток/с) идут на 15 % медленнее оценки,
      крупные — на 2–7 %. Это задержки запуска и HTTP на хосте стенда.
    - Из фактов GPU их не вывести, а мерить машину пользователя правило проекта запрещает.
      Записано как известный остаток в choice_constants.h.

18. **Кривая точности по квантам измерена (9B, KLD относительно Q8_0); на Ada квант выбирается по
    полезности внутри ступени правила #60.**
    - Кривая: Q6_K 0,0062; Q5_K_M 0,0106; Q4_K_M 0,0193; IQ4_XS 0,0283; Q3_K_M 0,068;
      UD-IQ3_XXS 0,107; UD-IQ2_M 0,161; UD-IQ2_XXS 0,334.
    - По перплексии Q3_K_M выглядит лучше IQ4_XS, по KLD — хуже, поэтому опираемся на KLD.
    - Варианты: «самый крупный, что влезает» (#60) / полезность по всем квантам / полезность внутри

    - Выбрано третье. Ступень (контекст на поток, сторона порога 3,5 бита) остаётся от #60,

    - Строка правила называет и выбранный квант, и самый крупный (`best_worth`).
    - На поколениях без права решать по-прежнему самый крупный.
    - **Это заметное изменение поведения по сравнению с #60: прошу владельца подтвердить или

19. **Ошибка кванта прибавляется к ошибкам переключателей линейно; корень из суммы квадратов —

20. **Чанк MoE решается по скорости, отдельно от флага точности.**

      но не его ошибку. Значит, решать его по KLD незачем.
    - Варианты: ждать флага точности / решать по скорости на эталонной карте за своим флагом
      `kMoeChunkTwoCards`.
    - Выбрано второе. Сейчас 35B на Ada → чанк 2048 и без флага точности.
      Закреплённый `--prefill-chunk` остаётся.

21. **Ветка «решает полезность» проверяется тестами при закрытом флаге.**
    - Раньше все проверки выбора по полезности стояли под `if (kKldTwoCards)` и не выполнялись.
    - Теперь у `choose` есть параметр `Gates`. По умолчанию — константы; тест открывает флаги
      и проверяет:
      - выбор кванта;
      - коды объяснений `lower_worth`, `quant_rule`, `tie_order`, `tie_context`;
      - чанк.
    - Заодно:
      - Q8_0 любой модели — эталон (0). Выше Q6_K кривая идёт прямой к 0, без скачка.
      - Противоречивые закрепления (`exact` и закреплённое f16-состояние) объясняются как есть,
        а не как «ничего не влезает».

22. **Открытый вопрос владельцу: слагаемые точности для других семейств.**
    - Слагаемые KV, активаций и состояния сняты на Qwen3.5-9B. Для Gemma, gpt-oss, Nemotron и

      решать и эти семейства.
    - Варианты: решать по перенесённым / для неизмеренных семейств оставлять умолчания семейства.
    - Пока оставил первое, потому что флаг всё равно закрыт.
    - Правильнее, по-моему, второе плюс замер перплексии хотя бы для Gemma 4 и 35B-MoE.
      Сделаю это вместе с открытием флага.

23. **Ошибка `fast` зависит от поколения карт. На Ada по правилу λ выигрывает `exact`. Это решение за тобой.**
    - Замер на тех же весах (Qwen3.5-9B Q4_K_M, артефакт один и тот же байт в байт), KLD против `exact`:

      | Карта | Поколение | KLD | top-1 |
      |---|---|---|---|
      | 4070 Ti | Ada | 0,0294 | 95,8 % |
      | 4090 | Ada | 0,0302 | 95,75 % |
      | 5070 Ti | Blackwell | 0,0039 | 98,5 % |

      Ошибка KV-кодеков на 4070 Ti и 5070 Ti сходится (в пределах 13 %).
    - Причина: какие вызовы префилла идут в int8, решают маршруты поколения (таблицы ad10x/gb20x и
      модель стоимости). Это свойство поколения, а не модели.
    - Решение: слагаемое активаций хранится по поколениям. Флаг точности больше не ручной: он
      открывается сам, когда за каждым решающим слагаемым стоят две карты. Не хватает только кривой
      квантов на 4070 Ti, она уже считается.
    - Следствие: как только кривая подтвердится, на Ada выбор для Qwen3.5-9B возьмёт `exact`.
      - На реальной смеси 4090 `exact` медленнее на 34 % (17,4 против 13,0 с), но точнее на 0,029 KLD.
      - При λ = 25 точка безразличия — 0,012 KLD. Значит, `exact`.
    - **Вопрос:** устраивает ли такая цена? Если нет, нужно снизить λ (около 8 — и `fast` остаётся).
    - **Лучший вариант, но он в движке, а не в выборе:**
      - на Ada держать префилл K-квантов в BF16, как это получается на Blackwell, а быстрый
        префилл GDN и f16-состояние оставить;
      - префилл — малая доля времени запроса 2048+512, так что потеря скорости, по оценке, около
        2 %, а ошибка должна вернуться к ~0,004;
      - нужен отдельный режим или маршрут, проверю замером и предложу отдельным PR.
    - Слагаемые для других семейств (запись 22): решает только семейство, на котором слагаемые
      сняты (Qwen 3.5 dense). Остальные остаются на правиле и умолчаниях, потому что перенос
      ошибки `fast` между семействами теперь заведомо ненадёжен.

24. **Ошибка `fast` на Ada и Turing — дефект движка; исправлен. Запись 23 снята.**
    - Причина:
      - ggml MMQ (префилл форматов ggml на 4090, 4070 Ti, 2080 Ti, 5090, L4, 4060 Ti, A10)
        записывал в q8_1 сумму исходных активаций, а скалярное произведение считал по
        квантованным;
      - у форматов с «минимумом» (Q4_0, Q4_1, Q5_1, Q4_K, Q5_K, Q2_K) два больших слагаемых
        гасят друг друга, и шум квантования не сокращался.
    - Как найдено. Q6_K и Q8_0 на Ada давали 0,004–0,005, Q4_K_M — 0,030. Затем по шагам на 4090:
      - без таблиц маршрутов — то же значение;
      - без тайла 128×128 и с тайлом producer-warp — то же;
      - без MMQ-префилла — 0,0039.
    - Исправление (отдельный PR, ветка `det/mmq-code-sums`): сумма блока считается по кодам
      (d·Σq), так же как в собственных W4A8-тайлах NInferno.
      - 9B Q4_K_M на 4090: KLD 0,0302 → 0,0040, top-1 95,75 → 98,44 %.
      - Скорость префилла та же: 5,66k → 5,67k ток/с.
    - Для выбора: слагаемое активаций снова константа модели (0,0039 на двух картах, два
      поколения). Ada решает, и `fast` остаётся при λ = 25: 0,004 KLD дешевле +34 % времени.
    - Вопрос владельцу из записи 23 снимается. PR выбора вливается только после PR исправления.

25. **Слагаемые точности — по семействам. Qwen-MoE получил свои, на двух картах.**
    - Замер: Qwen3.6-35B-A3B UD-IQ3_XXS на 4090 и 5070 Ti, карты сходятся в пределах 6 %.

      | Слагаемое | MoE | dense |
      |---|---|---|
      | KV int8 | 0,0033 | 0,00095 (в 3,4 раза меньше) |
      | KV fp8 | 0,0043 | 0,0028 |

      | KV nvfp4 | 0,0093 | 0,0098 |
      | `fast` | 0,0049 | 0,0039 |
      | доля состояния f16 | 0,0013 | — |

    - Вывод: переносить слагаемые между семействами нельзя (подтверждает запись 22). Теперь у
      каждого семейства свои строки, а чужие показываются только как оценка с пометкой «перенос».

      квантов 35B по 13–20 ГБ.
    - Gemma 4, gpt-oss и Nemotron по-прежнему на умолчаниях: `ninferno-perplexity` пока считает

26. **λ = 25 принято владельцем (25.10).** Если понадобится, меняется одна константа

27. **Сдвинутая ветка хаба: по умолчанию остаются сконвертированные веса (решение владельца, 24.10).**
    - Случай: модель скачана и сконвертирована, оригинал удалён (GUI удаляет его всегда, без
      `--keep-originals`), а на хабе ветка теперь указывает на другой коммит.
    - Правило владельца: перекачка — это много гигабайт, поэтому по умолчанию её не предлагаем.
    - Консоль (`ninferno-serve`, `ninferno-convert --fetch`): предупреждение, на терминале таймер
      10 с, затем старые веса.
      - `--accept-converted` принимает их как верные сейчас и впредь (запись `accepted.json`;
        снова спросит, только если ветка сдвинется ещё раз).
      - `--refetch` скачивает новый коммит, конвертирует и удаляет старую сборку после успеха.
    - GUI: в «Моих моделях» метка «на хабе новые веса» и две кнопки, «Оставить эти» и «Скачать
      новые». Хаб опрашивается не чаще раза в час на модель, с `--offline` не опрашивается.
    - Хаб недоступен: старые веса с предупреждением. Выдаваемые веса не зависят от сети (раньше в
      #93 недоступный хаб был ошибкой, а сдвиг сам скачивал новый коммит; заменено).
    - **Вопрос владельцу:** если оригинал не удалён (`--keep-originals`), запуск по имени хаба при
      сдвиге ветки сейчас сам докачивает новый коммит, как любая загрузка. При недоступном хабе
      это ошибка без `HF_HUB_OFFLINE=1`. Применить и здесь то же правило (старые веса с
      уведомлением)?

28. **Подмены маршрутов GEMM: видимы, а не ошибки (24.10).**
    - Аудит запасных путей (#93): вызов, который выбранный маршрут взять не может (буфер меньше
      нужного, невыровненный вход, неподходящая форма), молча шёл другим маршрутом — с другими
      байтами (A16 вместо int8-активаций, скалярное ядро) и скоростью. Писалась только первая
      подмена MMQ за процесс.
    - Замер (лабораторная печать каждой подмены): ctest; perplexity fast/exact; генерация со
      спекуляцией; сервер при 1 и 4 потоках — на Ada (4090: 9 моделей), Blackwell (5070 Ti:
      gpt-oss-20b + 6 квантов 9B), Turing (2080 Ti: 9B, 27B). **Ни одной подмены в работе
      продукта**; единственные — в тесте, который сам даёт буфер меньше нужного.
    - Решение: подмены детерминированы и на практике не срабатывают, поэтому не опасны. Делать
      их ошибками — рисковать отказом старта на картах вне лаборатории (Volta, A100, Hopper) без
      выигрыша. Каждая подмена, меняющая байты, теперь пишется один раз на пару маршрутов с
      фактами вызова и считается (`route_demotion_count`); тест проверяет, что вызов нужного
      размера не подменяется (det/route-demotion-visible).

29. **Сдвинутая ветка при неудалённом оригинале — то же правило (ответ владельца, 25.10).**
    - Вариант А: как при удалённом оригинале — старые веса с уведомлением (таймер в консоли),
      `--refetch` скачивает новые, `--accept-converted` запоминает; недоступный хаб — старые веса с
      предупреждением, не ошибка. Выдаваемые веса не зависят от сети.
    - GUI (уточнение владельца): фоновая загрузка **сама не стартует** — GUI предлагает её
      всплывающим окном, а в списке моделей помечает, что модель обновилась и её можно перекачать.
      По нажатию «Скачать новые» новый коммит качается и конвертируется **в фоне**,
      старая модель работает; новая сборка берётся при следующем запуске, а у запущенной модели —
      один перезапуск после окончания текущей работы. Старая сборка удаляется только после того,
      как новая поднялась.
    - Без зацикливания: на переход «коммит → коммит» не больше одного автоперезапуска; если новая не
      стартовала — возврат на старую, без новых попыток, запись в лог; новый сдвиг ветки во время
      загрузки не запускает новую загрузку сам, только отметку.

31. **Реестр спекуляции — онлайн, подписанный, читаемый (обсуждается, 24.10).**

**Факты (по коду).** Реестр драфтеров и профилей вшит в бинарник (`src/spec/data/drafter_registry.json`,

по умолчанию рекомендованное, переключатели показывают, что изменится.

**Предложение.** Один подписанный файл: по модели — драфтеры (репо@коммит, лицензия, размер) и таблица замеров
(класс карты × квант × вид × глубина → ток/с, приёмка, ускорение, дата, версия движка); рекомендация не хранится —
выводится клиентом из таблицы. Доставка как у манифеста релизов: сервер → кэш → копия установки; самая новая
подписанная версия понятной схемы; версия видна в логах/плане. Конвейер на нашей стороне — поэтапно.

## 40. W4A16-масштабы «мёртвых» строк, неточные в FP16 (вопрос владельцу, 26.10)

Найдено проверкой списка в продукте (4090): useful-quants/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-W4A16
(compressed-tensors int4 g64 sym, все эксперты упакованы) не стартует: «explicit grouping has incompatible
formats … experts/0/up bf16/cast_direct, experts/1/up u4_g64_zp_fp16/import_encoded».

Причина (проверено по байтам файла): у части экспертов up_proj есть «мёртвые» строки — масштабы
1,56e-38…1,96e-38 (BF16), коды до ±8, т. е. значения ~1e-37. Движок хранит масштабы int4 в FP16;
такие масштабы в FP16 неточны (уходят в 0), поэтому keep_published не сохраняет этого эксперта
«как опубликовано» (эксперт 0: 1890 из 77952 групп в 45 строках; эксперт 2: 84; эксперт 1: 0), а банк
экспертов MoE требует один формат на всех → ошибка планировщика (невнятная). Это тот же класс, что
SmolLM w4a16 (там F32-масштабы, неточные по-настоящему).

Варианты:
(а) оставить правило «слово в слово»: модель не поддерживается; исправить только сообщение — банк, где
    часть экспертов не сохраняется, отказывается штатной проверкой точности с причиной («масштабы не
    точны в FP16»), до этого — не падать в планировщике;
(б) уточнить правило без потери детерминизма: масштаб, у которого все восстановленные значения группы по
    модулю ниже 2^-100 (мёртвая группа), записывается как 0 — вклад в любой выход ниже разрешения BF16;
    это отражается в отчёте конверсии («N мёртвых групп записаны нулём»). Тогда модель запускается как
    опубликованная по сути.
Моё предложение: (б) с порогом и строкой в отчёте; (а) — если правило «слово в слово» важнее.

Дополнение к 40 (26.10): в конвертере уже есть решение разработчика — флаг `ninferno-convert --round-tiny-scales`
(«an integer site whose only inexact binary16 scales are below binary16's normal range is kept with them rounded
… changes those weights»), по умолчанию выключен; отказ теперь (det/expert-bank-kept) называет его прямо: «not kept:

## 43. DFlash-драфтер Gemma 4: скачивается, хотя сервер его не запускает (вопрос владельцу, 27.10)

Найдено кампанией пар (4070 Ti, unsloth/gemma-4-12b-it-GGUF с `--with-drafters`). Конвертер скачал

speculates with its MTP assistant only». Причина: в реестре вид `dflash` перечисляет движок `gemma4`.
Это сделано сознательно: инструмент мейнтейнера `ninferno-gemma4` (Session) запускает DFlash для
Gemma, и по его замерам в реестре лежат профили Gemma с DFlash. Но серверный Engine для Gemma
запускает только ассистента (`engine_support("gemma4_text").dflash_depth == 0`). Поэтому у
пользователя каждая конвертация чекпойнта Gemma 4 (драфтеры там включены по умолчанию) или GGUF с
`--with-drafters` скачивает драфтер, который сервер никогда не запустит.

Варианты:
- (а) план драфтеров подключает только виды, которые запускает серверный Engine (`engine_support`).
  DFlash для Gemma мейнтейнер берёт явно (`--drafter`).
- (б) оставить как есть.
- (в) научить Engine Gemma запускать DFlash. Это большая работа; польза по старым замерам Session
  неизвестна.

Предлагаю (а): это правка в одном месте (`plan_drafters`), профили Gemma с DFlash остаются для
Session.

## 43: разбор по просьбе владельца — зачем, где ошибка, единый источник (27.10)

**Зачем это было.** В проекте два исполнителя Gemma 4:
- **Session** (`models/gemma4/session.cu`, инструмент `ninferno-gemma4`) — исследовательский путь
  на один запрос. Он запускает ассистента, DFlash (общий `speculation::DFlashRound`), адаптивные
  глубины и ngram.
- **Engine** (`models/gemma4/program_family.cpp`, общий Program, то есть сервер) — путь на много
  потоков. При переносе Gemma на Program разработчик сделал только ассистента (MTP). Порт DFlash не
  доделан, хотя задел есть: цель Gemma уже умеет FeatureTap, а dense-семейство в том же Program
  запускает DFlash.

**Где ошибка.** Возможности записаны в трёх местах, и они разошлись:
1. `engine_support` (код, сверяется `static_assert` с каждым семейством) — правда сервера:
   Gemma = только MTP.
2. `kinds.dflash.engines` в реестре (данные, ещё времён Session) — «Gemma запускает DFlash».
   По нему конвертер скачивает z-lab DFlash для Gemma.
3. Профили Gemma в реестре настроены через Session: их выбор — dflash:7 / mtp:8:2. Для части
   профилей разработчик добавил заплатку `served` (лучший выбор, который запускает Engine), но не
   для всех.

**Последствие (проверено планом на master).** `unsloth/gemma-4-12b-it-GGUF` Q4_K_M:
- на RTX 5070 Ti: `spec auto -> plain (measured_plain … measured faster without speculation here)`;
- на RTX 4070 Ti: mtp:5.

Профиль «*» у 12B выбирает dflash:7 в рассуждениях и не имеет `served`. Меню отбрасывает
незапускаемое, и Gemma 12B на Blackwell идёт без спекуляции, с ложной подписью. По замерам
ассистент даёт ×2,4–2,8.

**Единый источник (предлагаю и делаю).**
- (а) Правда — `engine_support` (код, `static_assert` у каждого семейства). `Registry::supported`
  выводится из неё; поле `engines` у видов в реестре удаляется.
- (б) Проверка реестра тестом: каждый объявленный драфтер и каждый опубликованный выбор профиля
  запускаются сервером. Расхождение ловится при сборке, а не у пользователя.
- (в) Данные Gemma:
  - убрать объявления DFlash (Engine их не запускает);
  - в профилях с `served` выбор заменить на `served`;
  - где `served` нет, выбор, который сервер не запускает, заменить на лучший запускаемый того же
    профиля (`overall` / `non_thinking` — замеры той же карты). Где и такого нет — встроенный
    дефолт ассистента, но никогда не `plain` с подписью «замерено быстрее».
- (г) `served` и «профили Session» уходят вместе со старыми профилями в S4: замеры пар делает
  spec-tune на Engine, он мерит только то, что сервер запускает.
- (д) Порт DFlash в Engine Gemma — отдельная задача по данным: по старым замерам Session выигрыш
  +10–17 % только в рассуждениях на Blackwell. Решать после свежих замеров кампании.

## 45. GGUF-модели в GUI запускаются без отдельных драфтеров (вопрос владельцу, 25.10)

выше выбора брата: правило братьев занижает, а не завышает — безопасная сторона.

Третье семейство (4090, Gemma 4 12B GGUF, ассистент, mtp:5): UD-Q6_K_XL ×2,34 / ×2,80 против Q4_K_M
×2,28 / ×2,71 — единственный брат в классе (6 бит для 4-битного) завысил бы Q4_K_M на 3–4 %. Итого по трём
семействам: ближайший по битам брат в пределах −7…+4 % от замера; группа давала plain (−100 % выигрыша).
Тот же квант на двух картах Ada (4070 Ti / 4090): ×2,27 / ×2,28.

В продукте (4090), второе семейство: 27B GGUF UD-Q4_K_M без своей пары — master служит plain (группа),
ветка — mtp по брату UD-Q4_K_S (замер 5070 Ti); смесь 8 задач: 96,8 против 50,3 ток/с = ×1,92 (план без
thinking ×2,39, отношение 0,80 — обычный разрыв смеси с набором замера). Первое семейство (9B Q6_K): ×1,77.

Предложение (делается в черновом PR, решение владельца): между «своя пара» и «группа» — **пары брата**:
та же модель (репозиторий цели), тот же класс бит (<4 / ≥4), ближайший по битам на вес; профиль —
как из своей пары (profile_for_target), basis «preliminary», источник «registry sibling …». План и старт
берут одинаково: репозиторий **и коммит** — коммит листинга у плана (CLI и GUI), каталог
`ninferno/<commit>` артефакта у старта.

Ревизия (Codex на #128, 26.10): брат засчитывается только из **того же коммита** репозитория. Другой
коммит может хранить другие веса (новая версия модели, а не другой квант той же), и тогда защита
файнтюна была бы обойдена. Без известного коммита брата нет. Цена строгости: после любого коммита в
репозитории (даже README) братья перестают действовать, пока реестр не обновлён замером на новом
коммите, — до тех пор группа (консервативно). Своя пара от этого не зависит: она сличается по sha256
файлов. Сейчас (26.10) коммиты пар реестра совпадают с HEAD хаба у всех трёх семейств (9B, 27B,
Gemma 12B). Мягче и так же строго было бы сличать файлы брата с листингом нового коммита (sha256
брата всё ещё в репозитории → веса те же), но старт листинга не держит — одно правило для плана и
старта важнее.

Правка (Codex): ближайший брат, замеренный с другой версией подключённого драфтера, пропускается в
пользу следующего, замеренного с ним (а не уход в группу).

## 49. Незамеренное — не plain: выбор группы по выигрышу при приёме файнтюна (26.10)

Владелец (26.10, к 48): «спекуляцию выключать плохо, это всегда мимо; нужно, чтобы она находила, как
и другие оси, правильные значения».

**Что было.** Для цели без своего замера и без брата решает группа (тот же движок, вид драфтера,
класс бит, ≥2 карты). Правило группы: глубины, замеренные **у всех** пар группы; лучшая по средней
относительной скорости; вето в plain, если она не окупается **на самой слабой паре** при приёме
файнтюна (0,535 от замеренного).

**Проверка без новых замеров** (поставляемый реестр v119, 51 пара; каждая пара по очереди выключена
из своей группы и оценена по собственному замеру; 165 случаев: пара × вид драфтера × умолчание):

| Правило | plain | Средний выигрыш | От своего лучшего | При приёме ×0,63 (как WaveCut) |
|---|---|---|---|---|
| было | 102 | ×1,63 | 71 % | хуже plain: 0 |
| глубины на ≥2 картах + вето по слабейшей | 82 | ×1,74 | 76 % | 3 (худший ×0,99) |
| **среднее по группе при приёме файнтюна** | **0** | **×2,19** | **98 %** | 10 (худший ×0,83) |

Причины plain: у MTP-группы Qwen 3.5 (18 пар) нет ни одной глубины, общей всем; у ассистента Gemma
самая слабая пара (26B qat, ×1,29) вето-ет всех.

**Решение (ветка det/group-guarded-gain):** каждая глубина, замеренная на ≥2 картах, оценивается
средним по замерившим её парам выигрышем при приёме файнтюна; берётся лучшая; plain — только если ни
одна не даёт ×1,05 так. Её tok_s — этот выигрыш (оценка «preliminary», осторожная). Проигрыш
возможен лишь у моделей со слабым собственным ускорением (gpt-oss ×1,15–1,22, Gemma 26B qat ×1,29)
и только если их приём ещё на 37 % ниже.

Также к 48: строгое правило коммита у брата после правки README отдавало цель группе — теперь группа
даёт спекуляцию, а не plain, так что строгость не стоит выигрыша.

## 50. Выигрыш спекуляции на смеси задач ниже оценки плана: веса задач в оценке (26.10, вопрос)

Замер пары 27B UD-Q4_K_M + DFlash2 на 4090 (spec-tune, 26.10) совпал с опубликованным профилем:
dflash2:11 ×3,30 без рассуждений, ×4,02 с рассуждениями. А на смеси задач (8 задач без рассуждений,
mix_tasks) старт без флагов дал ×2,25 (113,2 ток/с против 50,3), то есть 0,68 оценки. У 9B на
4070 Ti / 4090 то же отношение было 0,83–0,87.

Причина — состав задач, не профиль. Оценка «без рассуждений» берёт математику, код и прозу поровну;
выигрыш по задачам очень разный:

| 27B, 4090 | математика | код | проза | рассуждения |
|---|---|---|---|---|
| dflash2:7 | ×4,6 | ×5,5 | ×1,86 | ×3,7 |
| mtp:5 | ×3,0 | ×4,3 | ×1,55 | ×2,6 |

Смесь богаче прозой (чат, перевод, письмо), поэтому её выигрыш ниже. Выбор между драфтерами от
этого почти не зависит: DFlash2 быстрее MTP на каждой задаче, и смесь это подтвердила (113,2 против
96,7). Но показанная в GUI скорость для смеси завышена в 1,2–1,5 раза.

Варианты (решение владельца):
1. Веса задач в оценке по типичной смеси (mix_tasks: доля прозы выше), один набор весов на все
   модели — оценка ближе к смеси, но зависит от выбранной «типичной» смеси.
2. Оставить равные веса, а в GUI показывать диапазон по задачам («проза ×1,9 … код ×5,5»).
3. Задача пользователя — вход выбора (чат / код / математика / смесь), веса по ней.

Предложение: 3, начиная с 2 — диапазон по задачам уже есть в данных профиля (замеры по разделам), и
он честно показывает, от чего зависит выигрыш.

## 51. Перенос выигрыша спекуляции на поколение без своих замеров (26.10, черновик)

Первая проверка на поколении, которого в реестре не было (Ampere, RTX 3060 12 ГБ). Сервер без флагов,
модель 9B GGUF Q4_K_M. План выбрал dflash:7 по брату UD-Q5_K_XL, замеренному на Ada (4070 Ti). Старт
подключил тот же драфтер.

На смеси задач скорость 84,3 против 52,9 ток/с: выигрыш ×1,59, решение верное. Скорость без
спекуляции план оценил точно: 53,7 против 52,9. А выигрыш завысил: обещал ×2,31 без рассуждений,
смесь дала 0,69 от этого, на Ada было 0,84.

Замер пары на 3060 (spec-tune) разделил причины:

| 9B + DFlash, без рассуждений | токенов за раунд | цена раунда, шагов plain | выигрыш |
|---|---|---|---|
| Ada 4070 Ti (UD-Q5_K_XL) | 3,77 | 1,63 | ×2,31 |
| Ampere 3060 (Q4_K_M) | 3,79 | 1,90 | ×2,00 |

Приём драфтера — свойство пары: токенов за раунд одинаково, хотя кванты разные. Цена раунда —
свойство поколения: проверка восьми строк и проход DFlash на Ampere на 16 % дороже относительно шага
без спекуляции. Отношение вычислений к пропускной способности у 3060 вдвое ниже, чем у 4070 Ti.

Значит, правило SPECULATION v4 «цена раунда переносится между картами, пока проверка ≤ 8 строк»
держится внутри Ada и Blackwell, но не между Ada и Ampere. Сейчас план переносит профиль чужой карты
целиком, то есть множитель ускорения.

Предложение: переносить порознь.
- Токены за раунд — от пары.
- Цена раунда — от своего поколения: поправка поколения для режима и глубины по парам, замеренным на
  обоих поколениях. Это медиана отношений цены раунда.
- Нет таких пар — как сейчас, с пометкой «перенесено с другого поколения».

Проверка правила: вторая пара Ampere, 9B MTP Q4_K_M (MTP и DFlash, у Ada есть). Держится ли поправка
×1,16 для другой пары и для MTP? Ожидание: MTP-раунд дешевле, поправка меньше. Решение после замера.

Итог (26.10, после ревью Codex #146): поправка поколения — константа поколения, а по AGENTS.md она
допустима только из замеров на двух и более картах поколения. У лаборатории одна карта Ampere (3060),
поэтому в поставляемом реестре поправка выключена (generation_round_costs пусто), пока вторая карта
Ampere не замерит общую цель. Свои пары 3060 служат как замеры. Механизм в #146 остаётся.
